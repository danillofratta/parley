# ADR-0013: MCP in the product and in development

- Status: Accepted
- Date: 2026-09-30

## Context

The AI agent needs context and actions owned by other services (conversation
history, handoff). Parley is also a showcase of current AI integration
practice, and support engineers would benefit from querying the platform from
AI clients such as Claude Desktop or Claude Code.

## Options

### Agent calls service REST APIs directly
Simple and familiar. Every new capability needs agent code changes, and tool
descriptions and schemas are hand-written for one framework.

### Agent reads other services' databases
Fast to build; breaks bounded contexts and database-per-service. Rejected.

### Services expose use cases as MCP tools; the agent is an MCP client (chosen)
Standard protocol with discovery, schemas and descriptions; the same server
serves the agent, Claude Desktop and Claude Code. Adds a protocol layer, a
security surface (tool misuse, prompt injection) and latency.

## Decision

- Conversations (.NET) exposes read tools and the `request_handoff` command
  tool; the Channel Gateway (Go) exposes read-only operational tools; the
  Agent Orchestrator (Python) consumes tools through `langchain-mcp-adapters`
  with an allowlist per graph.
- Tools are entry points to existing slices (no business logic in tools).
- The core Release 1 flow stays event-driven: `ConversationUpdated` carries the
  recent messages, so the agent works even if an MCP server is down. MCP is
  for on-demand context and explicit actions.
- Transport: Streamable HTTP at `/mcp`. Locally an API key on an internal
  network; in the cloud OAuth 2.1 (MCP authorization spec) or mTLS.
- Development: `.mcp.json` declares shared MCP servers for Claude Code, with
  tokens from environment variables.

## Consequences

- Positive: one integration mechanism for the agent and for humans' AI
  clients; tools reuse handlers, validation and invariants; showcases MCP in
  C#, Go and Python.
- Negative: synchronous runtime dependency for tool calls; new attack
  surface; tool descriptions become part of the contract and need tests.
- Simplifications compared with production: API key authentication locally;
  no rate limiting per tool yet.
